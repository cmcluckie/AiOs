# 170 lines

*The story behind AiOS, part 1.*

## What I was trying to do

Boot a computer and have it print one line.  That's it.  The oldest exercise
in the book, literally: it's on page one of the orange C book most of us
learned from.

Except I wanted one more thing, and it's the thing that turned an evening into
a project.  I wanted to be able to point at every line of code that ran between
the power button and that one line of text and say who asked for it, and why.

Linux can't do that.  Nobody can.  The smallest Linux you can build is still a
few hundred thousand lines, and most of them are there because somebody needed
them in 1997 and nothing is ever allowed to leave.  I'm not knocking Linux.
It's probably the most successful piece of software ever written, and it won
precisely because it kept everything.  But "keep everything" is the exact
opposite of what I was after.

So the rule is: nothing exists unless someone wrote down a reason.  Hello
world was the first test of whether that rule could produce a working machine
at all, or whether I was about to spend a weekend proving it couldn't.

## What got built

Three pieces, and I was stubborn about keeping them separate.

**The serial port.**  A virtual machine with no screen has one way to talk to
you: a serial port, the same kind of thing you'd have plugged a modem into
back when modems made that noise.  Linux's driver for it is a few thousand
lines, because it has to cope with every serial chip ever made, plus
terminals, flow control, locking, hot-plugging and so on.  Buried in there
are about ten lines that actually put a byte on the wire: wait until the chip
says it's ready, hand it the byte.  The AI went and found those ten lines and
the nine that set the chip up, and nothing else.  Fifty-seven lines in total,
every one of them traceable back to a line number in Linux, on a specific day,
at a specific commit.

**The loader.**  Something has to take over from the machine's firmware, get
the processor ready to run C, find the program and run it.  Normally that's
the kernel, and the kernel shows up with a scheduler, a memory manager, a
filesystem, a device model and a logging system, none of which hello world
asked for.  So this one doesn't bring any of that.  It sets up a tiny table
the processor insists on, gives itself four kilobytes of stack, copies the
program into place and calls it.  When the program's done, it asks the
processor to reset, and the virtual machine takes that as "we're done here"
and exits.  A hundred and six lines.

**Hello.**  Seven lines.  It gets handed a little table with two things on it,
write and exit, and it uses them.  It never touches the hardware.  The
compiled program is 43 bytes, which I find hilarious.

## The door

That little table is the part I care about most.  Hello doesn't talk to the
serial port.  It talks to the loader, and the loader talks to the serial port.
That's an extra step hello world absolutely does not need, and I insisted on
it anyway.

Here's why.  If hello world talked to the hardware directly, then the first
program that wanted a disk would have to throw hello world out and start over.
That's a cardboard box: fine until you want to build on it.  With the table,
the next program just gets a table with one more thing on it.  Nothing moves.
Hello keeps working.  We call the table the door, and it's how every program
on this thing is going to talk to the machine from now on.

## What we found inside Linux

Linux isn't really a pile of parts.  It's one giant program, and everything in
it assumes everything else is there.  Those ten lines that put a byte on the
wire are holding hands with the terminal layer, the device framework, the
memory allocator and the locking, and you can't pick them up without cutting
the hands.  So "just take what you need from Linux" turns out to mean "take a
few lines and rewrite the edges."  For a serial port that's an evening.  For a
network card it's going to be a lot more than an evening, and I'd rather say
that now than pretend otherwise.

One small thing I loved: Linux's version of those lines quietly turns every
newline into a carriage return plus a newline, because old terminals needed
it.  Ours doesn't, because the test is "exactly these fourteen bytes and
nothing else," and a byte nobody asked for is a failure.  You only notice that
stuff when you've promised to account for every single byte.

## What nobody asked for

Ten things in the build have no request behind them, and there's a file in the
repo that lists every one with why it's there and whether it could go.  Most
of them are the firmware's fault: the table the processor wants, the stack, a
particular wrapper format so the virtual machine will agree to load us, and
crashing the processor on purpose to shut down because the machine doesn't
have a power button.  A couple are devices the virtual machine insists on
including that we never touch.  And nine lines set up the serial chip in a way
the emulated chip doesn't actually need, but a real one would, so I kept them
and wrote down that no test can currently prove they're right.

That list is the product, really.  Hello world is just proof the list is
honest.

## Read along

If you want to see it for yourself, these are the files to read, in this order.  The links go to the exact version from this post.

1. [pool/CMP.hello@1/hello.c](https://github.com/cmcluckie/aios/blob/7c6a876/pool/CMP.hello@1/hello.c).  Seven lines.  Notice it never touches hardware.  It only calls the two things it's handed: write and exit.
2. [pool/CMP.loader@1/door.h](https://github.com/cmcluckie/aios/blob/7c6a876/pool/CMP.loader@1/door.h).  That's the door.  Two function pointers, write and exit.  Every program on the ladder gets this table, and later ones just get a longer one.
3. [pool/CMP.loader@1/loader.c](https://github.com/cmcluckie/aios/blob/7c6a876/pool/CMP.loader@1/loader.c).  Read it from the bottom up.  loader_main finds the program, copies it into place, and calls it with the door.  halt() is the reset trick.
4. [pool/CMP.serial.8250@1/serial8250.c](https://github.com/cmcluckie/aios/blob/7c6a876/pool/CMP.serial.8250@1/serial8250.c).  The 57 lines from Linux.  The comment at the top lists exactly which Linux lines each piece came from, and everything that was cut away.
5. [findings/0002.md](https://github.com/cmcluckie/aios/blob/7c6a876/findings/0002.md).  The list of everything nobody asked for, and why it's there anyway.  This is the honest part.

## Try this

Open the repo in Codespaces (or VS Code), open pool/CMP.hello@1/hello.c, change "Hello, world." to anything you like, and press F5 → AiOS: hello.  The machine prints your line instead.  You've just changed a program on an operating system without touching the operating system.

## Addendum: the tests

Every test written for the parts above: what it checks, what turns it red, and whether it has actually been run.  "Checked by hand" means it was run and compared, but not yet by the automatic test runner (plan section 4), which doesn't exist yet.  Until it does, these are honest notes, not a scoreboard.

**hello@1**

- [hello.exact-bytes@1](https://github.com/cmcluckie/aios/blob/main/tests/hello.exact-bytes@1.toml).  Checks: On start, the component writes the exact 14 bytes 'Hello, world.\n' to the console and nothing else, then exits.  Goes red when: the component's stdout, captured in isolation, is anything other than the 14 bytes 'Hello, world.\n'.  Status: Checked by hand, 2026-10-10: passed, 14 bytes exact.  Broken on purpose (one letter changed) and it went red at byte 11, as it should.

**loader@1**

- [hello.silent-boot@1](https://github.com/cmcluckie/aios/blob/main/tests/hello.silent-boot@1.toml).  Checks: From power-on to halt, no byte reaches the serial port that the program did not write.  Goes red when: the bytes on the VM's serial port from power-on to halt, minus the component's own output, are not empty.  Status: Checked by hand, 2026-10-10: passed, nothing on the port but hello's 14 bytes.
- [loader.door-layout@1](https://github.com/cmcluckie/aios/blob/main/tests/loader.door-layout@1.toml).  Checks: The door is a table of 32-bit function pointers, write at offset 0 and exit at offset 4; a later version of the door appends entries and never moves one.  Goes red when: compiled against door.h, offsetof(struct door, write) is not 0, offsetof(struct door, exit) is not 4, or a program built against door.h@1 fails under the current loader.  Status: Not run yet.
- [loader.halts@1](https://github.com/cmcluckie/aios/blob/main/tests/loader.halts@1.toml).  Checks: When the program calls the exit door or returns, every byte handed to the write door has left the serial port before the machine resets.  Goes red when: the machine process is still alive when the timeout expires, or the last byte the program wrote is missing from the serial capture.  Status: Checked by hand on every boot: the machine exits by itself.  Broken on purpose (a program that returns instead of exiting) and the loader still halted cleanly.
- [loader.runs-program@1](https://github.com/cmcluckie/aios/blob/main/tests/loader.runs-program@1.toml).  Checks: On entry the loader copies the machine's first module to 0x400000 and calls it with a pointer to the door, touching no device but the serial port.  Goes red when: a program that writes one marker byte through the door and exits, given as the machine's first module, produces no marker on the serial port.  Status: Not run as written yet (it needs a one-byte marker program).  Every program on the ladder exercises it.
- [loader.same-binary@1](https://github.com/cmcluckie/aios/blob/main/tests/loader.same-binary@1.toml).  Checks: The loader binary that runs one program on the ladder runs every other program on the ladder, byte-identical, with no change.  Goes red when: the loader built for any program on the ladder differs by one byte from the loader built for any other, or any program on the ladder fails under the loader built for another.  Status: Checked by hand, 2026-10-11: the loader built for hello and for Hanoi has the same hash.

**serial.8250@1**

- [serial.in-order@1](https://github.com/cmcluckie/aios/blob/main/tests/serial.in-order@1.toml).  Checks: Every byte handed to the write door appears on the serial port, in order, complete, and untranslated.  Goes red when: the bytes captured on the serial port differ in value, order or count from the bytes handed to the write door, including any 0x0d that was not handed to it.  Status: Not run on its own yet.  Every byte-exact boot exercises it, and all of them pass.
- [serial.origin-matches@1](https://github.com/cmcluckie/aios/blob/main/tests/serial.origin-matches@1.toml).  Checks: Every line range in the part's origin record names a file whose object id at the recorded upstream commit equals the recorded blob.  Goes red when: jig/upstream verify, run against a clone of upstream with the recorded commit, reports any range of this part as WRONG.  Status: Run, 2026-10-11, with jig/upstream verify: all 16 ranges match.  Not yet seen going red.

**machine.serial-only@1**

- [machine.no-peripherals@1](https://github.com/cmcluckie/aios/blob/main/tests/machine.no-peripherals@1.toml).  Checks: The machine presents the guest one 16550 serial port and no network, storage, display or input device; whatever else the hypervisor forces present is named in the as-built spec and touched by no component; a reset request ends the machine.  Goes red when: the device tree of a machine started with -S and queried once over a stdio monitor contains any device other than: isa-serial, isabus-bridge, ioapic, fw_cfg_io, kvmclock or kvmvapic, and the eight empty virtio-mmio transports microvm cannot omit.  Status: Checked by hand, 2026-10-10, against QEMU's own device list: passed.
- [machine.no-sockets@1](https://github.com/cmcluckie/aios/blob/main/tests/machine.no-sockets@1.toml).  Checks: The machine presents the guest one 16550 serial port and no network, storage, display or input device; whatever else the hypervisor forces present is named in the as-built spec and touched by no component; a reset request ends the machine.  Goes red when: strace of the machine process from start to exit records any socket, connect, bind or listen call.  Status: Not run yet.  Needs strace, which lives on the build machine that isn't set up yet.
