The story behind AiOS, part 4.

The thought that ruined my coffee

Sunday morning. Coffee, and a question I didn't have an answer to. Those fifty-seven lines we took from Linux's serial driver? Linux changes every day. When those lines change upstream, what happens to us?

Every Linux distribution lives with some version of this, and a huge chunk of their effort goes into it. They carry the entire tree, merge upstream constantly, and inherit every conflict and every bug fix that secretly depends on another bug fix. It's a treadmill with no off switch. I'd just signed up for the same treadmill, only smaller, and I had no idea how I'd ever pull those fifty-seven lines back in. That's the bit that actually worried me.

The question under the question

Then the product manager in me kicked in, and the real question showed up. It's the one I'd ask about any feature in any product I've ever owned. What was asked for? What got built? Why was it built, and what problem was it trying to solve? How was it built? And the one that matters most: how do we know it does exactly what it's supposed to do?

I'm not asking for a mathematical proof. I'm not building a verified microkernel here. I mean the basics. Somebody wrote down what this sliver of code is for, and somebody wrote unit tests and integration tests against that, so that when it changes, something goes red.

For our fifty-seven lines, as far as I can find, none of that exists. There's no spec. There isn't a single test file in the serial driver's folder, and the two terminal tests Linux does have are about other things entirely. What exists is the code, and the code is the only record of its own intent.

So I went looking for the history instead, and that's where it got a little sad. The header on the file says it was written at HP in 2004, "based on the 8250.c serial driver, Copyright (C) 2001 Russell King, and on early_printk.c by Andi Kleen." So the lines go back at least to 2001, through two other files, written by people solving problems I can only guess at. And when you go to git to follow the trail, it stops dead in April 2005. Linux's very first git commit says, and I love this, "Initial git repository build. I'm not bothering with the full history, even though we have it." (It's still there, if you want to see it: https://github.com/torvalds/linux/commit/1da177e.) Everything before that is in tarballs and old version control and mailing list archives, if you know where to dig. Just some person who wants to understand why these lines look the way they do can't follow the path.

I love history. I find that a bit sad. Some of the most important code on earth, and the reasons for it are scattered or gone.

So that's the deal for anything we take. It gets what it never had. A spec in one sentence that says what it's for. A test written off that spec that can fail. And a record of exactly where it came from, down to the commit, the date and the line numbers, so the next person who wants the history can just read it.

First, the mess

Before I could answer that, there was a mess to clean up. Two days in, and the repo already had our code and Linux's code sitting in the same folder under two different licences. The loader even had Linux's licence on it because fifteen of its lines were credited to Linux. That's how repositories turn into a swamp: not one bad decision, just never drawing the line.

So we drew the line. One folder is ours, MIT licence. Another folder is theirs, each piece under its own licence. Anything with even a single line from upstream lives in theirs. Then we looked at the loader again, properly, and it turned out to be ours after all: the structures it reads are a published boot interface, and the numbers in it come straight out of Intel's manual. Those aren't code, they're facts. The serial driver moved to the "theirs" folder where it belongs.

Update: that was wrong. Anything combined with Linux code has to be GPL, whatever folder it sits in, and a commenter rightly called it out. The whole repo is GPL-2.0 now.

Writing it down so a script can check it

Up to then, where the lines came from was a comment at the top of the file: "lines 86 to 98 of 8250_early.c." A comment is a promise nothing can check.

So now every piece we take from upstream has a small record next to it with everything needed to take it again from scratch: the repository, the exact commit, the commit's date, the file, a fingerprint of the file at that moment, the line ranges, who took it and when, and what got cut away. Sixteen ranges for the serial driver, right down to single lines.

A script reads every record and checks each fingerprint against a copy of Linux. If someone fat-fingered a line number or a hash, it says so. All sixteen are green.

The trick

And then the actual answer, which turned out to be sitting in git since 2013. git log -L follows a range of lines through history. You give it a file, a start line, an end line and a commit, and it tells you every commit since that touched those lines, even as other code moves them around the file.

So keeping up with Linux is one script. For every piece we took, for every range, ask git that question. Silence means nothing moved. A line means someone changed something we depend on, and a person goes and reads it and decides. Nothing ever merges on its own. If the change matters, we take the lines again as version 2, and everything built on version 1 keeps building exactly what it always built.

I tested it by pretending we'd taken the lines back in April 2025. It named the one upstream commit that touched them since. I put the real date back and it went quiet. I may have said "oh, that's lovely" out loud.

Distributions have the nightmare because they carry the whole tree. We carry line ranges, and a line range is a question git already knows how to answer.

Press play

Two smaller things from the same morning, both about making this usable by people who don't live in a terminal. Which, again, is most people.

VS Code now knows how to run each version of the system, so the Run and Debug dropdown lists them and F5 boots one. And the repo has a little config that makes GitHub's "Open in Codespaces" button give you a machine with everything already installed, right in your browser. Hit F5, watch it boot, never install a thing.

"Flavor," by the way, is our word for the set of programs one machine runs. Flavor hello is hello world. Flavor both is hello world and Hanoi at the same time, and the referee refuses it, because the loader only runs one program and the rung that changes that is still a ways off. The refusal is tested. That's very much the kind of thing this project is for.

Read along

If you want to see it for yourself, these are the files to read, in this order. The links go to the exact version from this post.

  1. lifted/PART.serial.8250@1/origin.toml. The record of where the 57 lines came from: repo, commit, date, file, fingerprint, line ranges. Enough to take them again from scratch.
  2. jig/upstream. The watch script. The interesting line is the one with git log -L in it. That's the whole trick.
  3. LICENSE. Read the bottom paragraph: what's ours, what's theirs, and where the line between them is.
  4. flavors/both.toml. A flavor that asks for two programs on one machine. The referee refuses it, and that refusal is on purpose.
  5. .devcontainer/devcontainer.json. The few lines that make the Codespaces button work, so nobody has to install anything.

Try this

Open the repo in Codespaces, press F5 and pick AiOS: both (refused until 9.6). You'll see the referee say no and tell you exactly why. That's what a dumb, honest gatekeeper looks like.
