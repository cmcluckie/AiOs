# The rulebook

*The story behind AiOS, part 2.*

## Why I started with rules

Part 1 had a nice number in it.  170 lines.  But small isn't the point, lots
of things are small.  What makes this different is that those 170 lines came
out of a process, and the process is really the whole project.  So this one's
about the process, written for people who would rather not read a repository.
Which is most people.  Which is fair.

Most projects start with code and add rules later, usually right after
something blows up.  I went the other way.  The repository started with a
document I'm calling the constitution, and no code got written for the first
eight commits.  It says what a machine is for, what's allowed in, and what has
to be true before anything gets in.  Thirty years of watching software grow
sideways will do that to you.

## The ten rules

There are ten rules at the top, and nobody gets to vote them away.  Plain
English version: nothing exists without a written purpose.  There's exactly
one way in.  Source code only, nothing pre-compiled.  Everything gets reviewed
before it gets in.  Once it's in, it's ours, and we don't sit around waiting on
someone upstream to fix it.  The core provides the levers and never decides
when to pull them.  The smart thing that suggests changes and the dumb thing
that approves them are never the same thing.  Every test is written so it can
fail.  Nobody's confidence counts, only their track record.  And everything
expires.

That last one is the heart of it.  Linux can add forever and never take
anything back out.  Here, if nobody's using it anymore, it goes.  Same parts,
opposite rule.

## Why is there a firewall?

This is the question that got me started down this road, so it deserves a
spot.

A firewall is a guard standing in front of a door, checking everyone who tries
to come through.  Fine.  Useful, even.  But I keep asking: why is the door
there?  If nothing on the machine asked to listen on that port, why does the
port exist at all?  We build an operating system that can do everything, open
up every possibility, and then bolt a guard on the front to close most of them
again.  That's backwards.  It's like building a house with forty doors and
then hiring forty security guards.

Here, nothing listens unless a petition asked for it, with a reason, and when
that reason goes away so does the listener.  The machine hello world boots on
doesn't even have a network card.  Not a blocked network card.  No network
card.  And there's a test written to go red if one ever shows up.

So is a firewall necessary when the functionality isn't in the product?  I
don't think it is.  You can't attack a door that was never built.  The day a
petition actually needs the network, the "firewall" is just the petition
itself: this program may talk to that address, for this reason, and nothing
else.  The rules live in the same place as everything else, and they expire
like everything else.

## The petition

So how does something ask to get in?  It files a petition.  Yes, I know.  Bear
with me.

A petition is a small structured file, and the one rule I fought hardest for is
that it has no prose in it.  None.  It says: here's the purpose I serve, here
are the things I need to touch, and for each one, here's the one-sentence spec
that explains why I need it.  Here are the parts I'm made of.  Here are the
tests that can prove me wrong.  Every item is a short code that points at
exactly one definition somewhere else.

The no-prose thing sounds fussy.  It turned out to be the best decision in the
whole design.  A request written in English can be argued with, and everyone
who's ever sat in a change review meeting knows how that goes.  A request
written as codes can be checked by a script with no opinions.  If a permission
doesn't have a spec behind it, it's rejected, and no amount of "but it's
really important" in a comment changes that.

## The referee

The part that checks the petitions is called the referee, and it's dumb on
purpose.  No AI in it.  It doesn't know what a serial port is.  It knows how to
follow a code to a file, check the file is there, and apply eleven rules that
all look like "every X must have a Y."  When it says no, it gives you a rule
number and a code, and that's all you get.  "Rule 1: missing
CMP.serial.8250@1."  Charming.

This is my answer to the question everybody's asking about AI writing
software: what stops the clever thing from talking its way past the gate?
Here, the clever thing never gets near the gate.  The AI proposes.  The
referee, which can't be persuaded because it can't understand, decides.  And
my signing key sits above both of them.

## Thirteen holes

The first time I wrote a real petition against those rules, the rules couldn't
say thirteen things the petition needed to say.  There was no way to name a
purpose.  No way to say "this depends on nothing at all."  No way to put a
requirement on a part you depend on instead of on yourself.  No way to say how
long a test gets to run before it counts as stuck.  And my favourite: the
review signatures were stored inside the file they were signing, so every
signature changed the file the next person had to sign.  Oops.

I wrote all thirteen down, fixed eleven, and published the rulebook as version
2 before a single line of code existed.  Those thirteen holes are probably the
most useful thing I've produced on this project.  Every project has them.
Almost nobody writes them down.

## Why an operating system, of all things

An operating system is the one piece of software that says yes or no to every
other piece of software.  Today it says yes to whatever got in at install time
and then never asks again.  The constitution turns that into a question that
never stops being asked: who asked for you, why, and is that still true?

Every program on the ladder from here on is a program answering that question.

## Read along

If you want to see it for yourself, these are the files to read, in this order.  The links go to the exact version from this post.

1. [constitution/tenets.md](https://github.com/cmcluckie/aios/blob/6b41afe/constitution/tenets.md).  The ten rules.  Short.  Everything else in the repo answers to these.
2. [petitions/0000.toml](https://github.com/cmcluckie/aios/blob/6b41afe/petitions/0000.toml).  Hello world's petition.  No prose: just codes.  Find the line that says it needs to write to the console, and the reason code next to it.
3. [specs/hello.1@1.toml](https://github.com/cmcluckie/aios/blob/6b41afe/specs/hello.1@1.toml).  That reason code, opened up.  One sentence saying exactly what hello world must do.  Precise enough to fail.
4. [schema/petition.md](https://github.com/cmcluckie/aios/blob/6b41afe/schema/petition.md).  Scroll to "Relation rules the referee enforces".  Eleven rules, all shaped like "every X must have a Y".  That's the whole referee.
5. [findings/0000.md](https://github.com/cmcluckie/aios/blob/6b41afe/findings/0000.md).  The thirteen holes the first petition found in the rules, and what was done about each one.

## Try this

Pick any line in petitions/0000.toml with a code on it and follow it: code → file → the next code inside that file.  Every chain ends at a sentence a person wrote.  If you find one that doesn't, that's a finding, and I'd love to hear about it.

## As built

Nothing was built in this part; it's the rulebook.  The rulebook is checked by the referee, whose own tests come with plan section 3.

## Addendum: the tests

No code, so no code tests in this part.  The rulebook's own check is that every petition in the repo passes the referee, and the refusals are tested by hand: the flavor that asks for two programs is refused, and a petition naming a part that doesn't exist is refused by rule and code.
