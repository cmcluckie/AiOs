2. Title

Where's the kernel?

3. Article

The story behind AiOS, part 8.

Who's been checking the homework

Up until now, the testing on this project has been done by the AI. It runs the program, looks at what comes out, compares it with what it should be, and tells me it passed. That's fine for getting started. It is not where we want to be. The whole point of writing tests down is that something other than the author runs them, every time, and doesn't get tired or optimistic.

So this part is the testers. A runner that boots every program and checks every byte, and a script that breaks the code on purpose to prove the tests would notice. But to decide what to test, I first had to understand what the parts actually are. And that's where the light bulb went on for me about what actually makes an operating system.

Where's the kernel?

I kept asking the AI where the kernel was. The honest answer is there isn't one yet.

It took me a few goes to get there, because I kept asking the question as if there had to be one. What we have is a loader. The firmware wakes the virtual machine up and hands control to the loader, and from then on the loader is the only thing in charge. It sets the processor up, copies the program into memory, gives it a little table of things it's allowed to ask for (write, exit, memory, read), and runs it. When the program says it's done, the loader shuts the machine off.

If you know a bit about how processors work (I know just enough to be dangerous), the processor is already in protected mode, the 32-bit mode PCs have had since the 386 (modern ones go one step further, to 64-bit). The loader turns that on in its first few instructions. What it doesn't do is the part that makes a kernel a kernel: run the program with less power than itself. Right now the program and the loader have exactly the same keys to the building. There's no scheduler, no interrupts, no protection. With one program on the machine, none of that has a job yet.

It's a lot closer to the first operating systems on micro PCs than to Linux: a resident program directing traffic. The old word for it is a monitor. When a second program has to share the machine, that's when the kernel shows up (plan 9.6), and you'll be able to point at the exact commit.

And why does the loader do any of this? Because we told it to. Every program on AiOS has a petition, and every flavor of the system is built from the petitions for the programs it runs. No program, no petition. No petition, nothing gets built.

How a byte gets out

Here's the bit I find really interesting. The actual write, the code that puts a byte on the wire, lives in the serial driver, the lines we took from Linux. The program never touches it. Hello world hands its 14 bytes to the loader through the door. The loader hands them to the driver. The driver pokes them into the serial chip one at a time.

So the loader is the handoff point. Today every write goes to one place, the serial port. As this grows, that routing is where it gets interesting: a write could go to a screen, a file, a network, and the program wouldn't know or care. That's what the door is for. The day the loader starts deciding where a write goes, it's starting to become a kernel.

Two kinds of tests

So what do you test? Two things, really.

The driver on its own: does it put every byte on the wire, in order, untranslated, and does it take every byte off the wire it's handed? That's the unit test.

Then everything together: boot the machine with the real loader, the real driver and the real program, type into it if it needs typing, capture every byte that comes out, and compare. That's the integration test, and most of our tests are that shape.

One honest wrinkle. The normal way to unit test a driver is to swap the real hardware for a fake one that records everything. We can't do that without editing the Linux lines, and the lifted code doesn't get edited. So instead, the runner asks the virtual machine to log every single read and write to the serial chip's registers while the real thing runs. Same evidence, nobody touches the driver.

The second opinion

For hello world you know the right answer by looking. For Conway's Game of Life after 200 generations, you can't: it's 1,992 bytes of grid. When I asked why the testing needed Python, this was the answer. We need a second opinion.

Think of two people adding up the same restaurant bill, separately. If they both get the same total, you trust it. If they don't, somebody made a mistake and you go find it. So for Life, Hanoi and the calculator there's a second version of each program, written in Python from the same rules, run on a normal computer. Its answer is saved as a file. The runner boots the real program and compares every byte against that file. That's exactly how the calculator bug in part 6 got caught: the second opinion said "too big", ours said 1215752191.

The catch is that both people were the AI. If it misread a rule, both versions carry the same mistake and happily agree. That's evidence, not proof. The saved answers are in the repo, along with the programs that made them, so anyone can check them against someone else's.

And the jig, the machine that builds AiOS, still doesn't need Python. It only compares bytes.

Breaking it on purpose

A test that has never failed proves nothing. So the other half of this part is a script that breaks the code on purpose, one small change at a time, and checks the right test goes red. Change "Hello" to "Jello". Lose the newline. Make hello never exit. Delete the overflow check from the calculator again. Copy the program 16 bytes off from where it should run. Give the machine a device nobody asked for. Make it open a network socket.

24 sabotages. 21 caught. The three that weren't are the best part.

The serial driver normally waits for the chip to say "ready" before each byte. Take that wait out and every single test still passes, because the virtual chip is always ready. On a real chip, you'd lose bytes. Nobody ever wrote down that the driver must wait, so nothing checks it. Same story for the setup code that tells the chip to use 8-bit bytes. The third one is a test that's honest but blind: the calculator only ever asks for one keystroke at a time, so a bug that only shows up when you ask for more than one byte sails past its test. It's caught by a different test instead.

None of those are fixed in this part. They're written down (findings 0007), and the first two need someone, me, to write the rule they break. That's how it's supposed to work: the system tells you exactly where your safety net has holes.

Where that leaves us

Every test we've written now runs with one command, and every one passes. Most of them have been shown failing on purpose. The "checked by hand" notes in the earlier parts' addenda were true when they were written; from here on, the addendum says what the runner says.

The fine print: all of this ran under software emulation in a container, not on the jig and not on real virtualisation. The jig is still a thing I need to sit down and install.

If this is where things start to come together for you too, that makes two of us.

Read along

  1. jig/test. The runner. The comment at the top explains every kind of test it knows. Look for trace: that's the register log standing in for a fake chip.
  2. tests/results.txt. What the runner said, test by test, and what it ran on.
  3. tests/mutations.txt. Every sabotage, one per line, with what it breaks. The "survives" lines are the holes.
  4. tests/fixtures/life_ref.py. The second opinion for Life, in about 20 lines of Python. Put it next to pool/PART.life@1/life.c and compare.
  5. findings/0007.md. What the runner and the sabotage found, including the three survivors.

Try this

Open pool/PART.hello@1/hello.c and change "Hello" to "Jello". In a terminal (the Codespaces one works), run sh jig/test hello. You'll get FAIL, and it tells you the very first byte that's wrong. Change it back and run it again. Then try sh jig/mutate hello to watch the sabotage script do the same thing five ways.

Addendum: the tests

Every test in the repo, from tests/results.txt and tests/mutations-results.txt. All of them ran under software emulation, not on the jig.

calc@1

  • calc.transcript@1. Checks: Given a sequence of typed bytes, the component writes exactly what an independent reference implementation of the same reverse-Polish rules writes for that sequence, including echo, errors and the final bye, and exits only on q, quit, Ctrl-C or Ctrl-D. Goes red when: with tests/fixtures/calc.in fed to the serial port, the bytes written differ from what tests/fixtures/calc_ref.py writes for the same input, or the machine is still running at the timeout. Status: Passed by the runner (software emulation): 424 bytes, exact. Mutations caught: 1.

hanoi@1

  • hanoi.exact-moves@1. Checks: On start, the component writes exactly the 15 moves of the standard four-disk solution, one per line as 'Move disk N from X to Y', 360 bytes, nothing else, then exits. Goes red when: the component's output, captured in isolation, differs from the 360 bytes a reference solver produces for four disks. Status: Passed by the runner (software emulation): 360 bytes, exact. Mutations caught: 1.

hello@1

  • hello.exact-bytes@1. Checks: On start, the component writes the exact 14 bytes 'Hello, world.\n' to the console and nothing else, then exits. Goes red when: the component's stdout, captured in isolation, is anything other than the 14 bytes 'Hello, world.\n'. Status: Passed by the runner (software emulation): 14 bytes, exact. Mutations caught: 5.

life@1

  • life.exact-output@1. Checks: On start, the component writes the population after 200 generations of the centred R-pentomino in a 256 by 96 universe with dead edges, the middle 80 by 24 cells as '#' and '.', and the result of asking for 128 MiB, exactly as a reference implementation produces them, then exits. Goes red when: the component's output, captured in isolation, differs from the 1992 bytes an independent reference implementation produces for the same rules, seed, universe and generation count. Status: Passed by the runner (software emulation): 1992 bytes, exact. Mutations caught: 1.

loader@1

  • hello.silent-boot@1. Checks: From power-on to halt, no byte reaches the serial port that the program did not write. Goes red when: the bytes on the VM's serial port from power-on to halt, minus the component's own output, are not empty. Status: Passed by the runner (software emulation): 14 bytes, exact. Mutations caught: 1.
  • loader.door-layout@1. Checks: The door is a table of 32-bit function pointers, write at offset 0 and exit at offset 4; a later version of the door appends entries and never moves one. Goes red when: compiled against door.h, offsetof(struct door, write) is not 0, offsetof(struct door, exit) is not 4, or a program built against door.h@1 fails under the current loader. Status: Passed by the runner (software emulation): door layout holds in 3 versions. Mutations caught: 1.
  • loader.halts@1. Checks: When the program calls the exit door or returns, every byte handed to the write door has left the serial port before the machine resets. Goes red when: the machine process is still alive when the timeout expires, or the last byte the program wrote is missing from the serial capture. Status: Passed by the runner (software emulation): flushed after the last byte. Mutations caught: 1.
  • loader.runs-program@1. Checks: On entry the loader copies the machine's first module to 0x400000 and calls it with a pointer to the door, touching no device but the serial port. Goes red when: a program that writes one marker byte through the door and exits, given as the machine's first module, produces no marker on the serial port. Status: Passed by the runner (software emulation): 14 bytes, exact. Mutations caught: 1.
  • loader.same-binary@1. Checks: The loader binary that runs one program on the ladder runs every other program on the ladder, byte-identical, with no change. Goes red when: the loader built for any program on the ladder differs by one byte from the loader built for any other, or any program on the ladder fails under the loader built for another. Status: Passed by the runner (software emulation): one loader, 5b4601bf374c5f45. Mutations caught: none yet (findings 0007).

loader@2

  • loader.alloc-in-ram@1. Checks: Every block the alloc door returns lies inside a region the firmware's memory map marks RAM, above the end of the program, and overlaps no earlier block, the loader, or its stack. Goes red when: a program that allocates blocks until refused and prints each block's address and size shows any block outside the RAM region containing the program, below the program's end, or overlapping another. Status: Passed by the runner (software emulation): 59 blocks, all inside RAM, none overlapping. Mutations caught: 1.
  • loader.alloc-refuses@1. Checks: When the alloc door cannot satisfy a request it returns 0 and changes nothing; it never halts, never returns memory outside the region, and a later smaller request can still succeed. Goes red when: a program that asks for more than the machine has gets a non-zero pointer, or the machine does not continue to a later smaller request that succeeds, or the machine halts before the program calls exit. Status: Passed by the runner (software emulation): 128 MiB refused, 16 bytes still granted after the refusal. Mutations caught: 1.

loader@3

  • loader.read@1. Checks: The read door waits for at least one byte, then returns the bytes already received, in order, up to the requested count, and never more; write, exit and alloc keep their offsets and their behaviour from PART.loader@2. Goes red when: with tests/fixtures/calc.in fed to the serial port, PART.calc@1 under this loader does not produce the reference transcript, or hello, hanoi or life under this loader differ by one byte from their outputs under the loader they were built for. Status: Passed by the runner (software emulation): 4 programs byte-identical under loader@3. Mutations caught: 1.

machine.serial-only@1

  • machine.no-peripherals@1. Checks: The machine presents the guest one 16550 serial port and no network, storage, display or input device; whatever else the hypervisor forces present is named in the as-built spec and touched by no component; a reset request ends the machine. Goes red when: the device tree of a machine started with -S and queried once over a stdio monitor contains any device other than: isa-serial, isabus-bridge, ioapic, fw_cfg_io, kvmclock or kvmvapic, and the eight empty virtio-mmio transports microvm cannot omit. Status: Passed by the runner (software emulation): 13 devices, all on the list. Mutations caught: 1.
  • machine.no-sockets@1. Checks: The machine presents the guest one 16550 serial port and no network, storage, display or input device; whatever else the hypervisor forces present is named in the as-built spec and touched by no component; a reset request ends the machine. Goes red when: strace of the machine process from start to exit records any socket, connect, bind or listen call. Status: Passed by the runner (software emulation): 1060 syscalls traced, none on the network. Mutations caught: 1.

serial.8250@1

  • serial.in-order@1. Checks: Every byte handed to the write door appears on the serial port, in order, complete, and untranslated. Goes red when: the bytes captured on the serial port differ in value, order or count from the bytes handed to the write door, including any 0x0d that was not handed to it. Status: Passed by the runner (software emulation): 512 bytes, exact. Mutations caught: 1.
  • serial.origin-matches@1. Checks: Every line range in the part's origin record names a file whose object id at the recorded upstream commit equals the recorded blob. Status: Passed by the runner (software emulation): PART.serial.8250@2: ok include/linux/serial.h 26-29. Mutations caught: 1.
