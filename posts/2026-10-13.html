The story behind AiOS, part 3.

The problem

Towers of Hanoi. Three pegs, a stack of disks, move the whole stack to another peg one disk at a time without ever putting a big one on a small one. Four disks takes fifteen moves, and the slick way to find them is a function that calls itself twice. Every CS student wrote it. Most of us wrote it in the same week we learned what a stack was, and then spent the next week blowing ours up.

Full disclosure on the bias here. Recursion was one of my favourite things in college, and it's still one of the ideas in computer science I love the most. You solve a big problem by solving a smaller copy of the same problem, and you just trust that the smaller one works. To move four disks, move three out of the way, move the big one, move the three back on top. How do you move three? Same way. The whole solution is about six lines and it never stops feeling a little bit like magic to me. So yes, I picked Hanoi partly because I wanted recursion in here.

The other reason: it needs nothing new from the machine. It writes, it stops. Exactly what hello world needed.

Which made it the perfect way to test the claim that matters most in this whole project: that you can add a program to this thing without changing the operating system.

Why that claim is the whole bet

Friday night, the kernel conversation flipped the entire plan upside down, and the question I kept circling back to was this. If hello world owns the whole machine, what happens when the second program shows up? The honest answer was "you throw hello world away and start again." That's a cardboard box, and I'm not doing magic swaps. I want bricks.

So hello world was built as a tenant from day one. It gets a little table with two things on it, write and exit, and it never touches anything else. The loader is the landlord, even with exactly one tenant and nothing to do all day.

Hanoi is the second tenant. If I got this right, the landlord shouldn't even notice.

What got built

About thirty lines of C. One function fills in a line that says "Move disk N from X to Y" and writes it through the door. Another calls itself for one fewer disk, moves a disk, and calls itself again. The entry point runs it for four disks and calls exit. No new door entries. No new permissions. Its petition asks for the same two things hello world asked for, and the same loader.

The build compiles the loader, then compiles Hanoi against it. Then it compiles the loader again for hello world. Both loaders come out with the same hash. Not similar. The same bytes. The diff to the operating system is zero lines.

Recursion with no safety net

Nothing dramatic happened, which was the point, but two things made me smile.

Recursion needs a stack, and the loader gives the program four kilobytes. For a recursion four levels deep that is absurdly generous. But there's no check on it. A program that recursed a few thousand levels deep would just walk off the end of its stack into the loader's own memory, and nothing would stop it. Protection is something a landlord provides when there are tenants to protect from each other. With one tenant, we just write down that it isn't there.

And there's no printf. No C library at all. So "Move disk 4" gets made by poking a digit into a template string. Four disks, one digit. That's the kind of corner you cut when you're being honest about what the program is actually for.

One small cleanup

Hello world had its own file telling the compiler how to lay the program out in memory. Hanoi would've needed an identical copy. Two identical files is the universe telling you they belong somewhere else, so it moved: it's really the loader's definition of "what a program looks like," so now it lives with the loader and every program on the ladder uses it. Git spotted the move and recorded it as a rename, which pleased me more than it should have.

The ladder

With two programs on one loader, the rest of the plan finally had a shape. Each next program asks for exactly one new thing: memory, then input, then a clock, then a disk, then two programs at once. Each one adds a door and never moves an old one, and every earlier program has to keep booting on every newer loader. That last bit is now a test that runs every time the loader changes, and Hanoi is why it exists.

Read along

If you want to see it for yourself, these are the files to read, in this order. The links go to the exact version from this post.

  1. pool/PART.hanoi@1/hanoi.c. Look at the hanoi function. Six lines, and it calls itself twice. That's the whole solution.
  2. petitions/0001.toml. Put it next to petitions/0000.toml. Same permissions, same loader. Nothing new was asked for.
  3. pool/PART.loader@1/program.ld. The file that tells the compiler what a program looks like. It moved here from hello world, because it belongs to the loader.
  4. specs/loader.4@1.toml. The rule this post is really about: the loader that runs one program runs all of them, byte for byte.

Try this

Open pool/PART.hanoi@1/hanoi.c, change DISKS from 4 to 5, and press F5 → AiOS: hanoi. You'll get 31 moves instead of 15. Then look at specs/hanoi.1@1.toml, which still says 15: you've just made the test go red, on purpose, which is exactly what tests are for.

Addendum: the tests

Every test written for the parts above: what it checks, what turns it red, and whether it has actually been run. "Checked by hand" means it was run and compared, but not yet by the automatic test runner (plan section 4), which doesn't exist yet. Until it does, these are honest notes, not a scoreboard.

hanoi@1

  • hanoi.exact-moves@1. Checks: On start, the component writes exactly the 15 moves of the standard four-disk solution, one per line as 'Move disk N from X to Y', 360 bytes, nothing else, then exits. Goes red when: the component's output, captured in isolation, differs from the 360 bytes a reference solver produces for four disks. Status: Checked by hand, 2026-10-11, against a separate Python solver: passed, 360 bytes exact.

loader@1

  • loader.same-binary@1. Checks: The loader binary that runs one program on the ladder runs every other program on the ladder, byte-identical, with no change. Goes red when: the loader built for any program on the ladder differs by one byte from the loader built for any other, or any program on the ladder fails under the loader built for another. Status: Checked by hand, 2026-10-11: the loader built for hello and for Hanoi has the same hash.
