# The machine listens

*The story behind AiOS, part 6.*

## Why a calculator

Every program so far talks and never listens.  Hello world, Hanoi and Life
all start up, say their piece, and leave.  The next rung is input: a program
that sits there and waits for a person.

The obvious textbook pick was guess-the-number, and it has one small problem
here: it needs a random number, and this machine has no clock and nothing
random in it yet.  That's a later rung.  So we went with the reverse-Polish
calculator instead, which is two textbook chapters for the price of one:
input, and the stack.  "3 4 +" pushes 3, pushes 4, adds them.  "2 *" doubles
it.  No brackets, no order of operations to fuss over, which is why HP put it
in their calculators in the seventies and why every data structures course on
earth uses it to teach stacks.  If you owned one of those HPs, you're smiling.

## A short history of me and input

Input has always been the part of programming with a bit of personality for
me.  In C, I grew to really appreciate stdio.h.  printf, scanf, getchar: plain
functions with plain names that did what they said.  You could read the line
and know what it did.

Then I graduated to C++, and the first thing it handed me was this:

    cin >> x;

Two greater-than signs, pointing at a variable, somehow meaning "read a number
from the keyboard and put it here."  It made no sense to me then.  It's an
operator that normally shifts bits, borrowed and dressed up to mean "flow into."
I learned to use it.  I never learned to love it, and if I'm honest it's still
a bit of a mystery to me today.

Which makes this rung a little funny.  On AiOS there's no stdio and no `>>`.
There's no library at all.  The program asks the machine for one byte, gets
one byte, and builds everything else itself: the line, the echo, the backspace,
the numbers.  All the stuff stdio did for me, and `>>` did mysteriously, is
right there in the open.

## What got built

The calculator is about a hundred and seventy lines of C.  It keeps a stack of
64 numbers, reads one key at a time, builds up a line, and when you hit Enter
it splits the line into pieces.  A number goes on the stack.  An operator
takes two off and puts the answer back.  `dup`, `swap`, `drop` and `clear` do
exactly what they sound like.  After every line it shows you the top of the
stack.  `q` quits.

The arithmetic is the easy part.  The interesting part is everything your
terminal normally does for you without you ever noticing.  When you type on a
normal computer, the operating system shows you your keys, deals with
backspace, and hands the program a whole line when you hit Enter.  Here
there's nothing in between, so the program does all of it itself.  Every key
you type gets echoed back as it arrives.  Backspace erases with a little
back-space-back dance.  And Enter is a different key depending on who's
typing: a person sends one byte, a script sends another, and Windows, being
Windows, sends both.  The emulator deliberately puts your terminal in a mode
where nothing gets done for you, precisely so the machine has to handle it.
Nothing hides anything.  I kind of love that.

## What changed underneath

Two parts moved up a version, and the old versions stayed exactly as they
were, because that's the rule.

**The serial driver, version 2.**  Linux's early console driver has a reading
function almost nobody uses.  It asks the chip "got a byte waiting?" by
checking one bit, and if so, takes the byte.  Seventeen lines in Linux, wrapped
in a bunch of console plumbing and a config switch.  We took the question and
the read and left the plumbing.  The new version has its own record of where
it came from, and the upstream check now verifies both versions: thirty-four
ranges, all green.

**The loader, version 3.**  The door gets a fourth entry, `read`: wait for one
byte, then grab anything else that's already arrived.  It just keeps asking
the chip.  No interrupts, because nothing has asked for the machine to do
anything else while it waits, and with one program, waiting is the whole job.
Thirteen lines.  `write`, `exit` and `alloc` didn't budge.

## The test that went red

This is the part I want to remember.  Before we booted the calculator, the AI
wrote it a second time in Python, from the same rules, as a reference.  The
test types the same keys into both and compares every byte that comes out.

It failed at byte 320.  I'd typed 99999999999 to make sure it would say "too
big."  Instead it cheerfully told me "= 1215752191."

The code built the number up digit by digit and checked whether it was too big
after each multiply by ten.  On a 64-bit machine, no problem.  On this one,
the number box is only 32 bits, so the multiply wrapped around before the
check ever saw it, and the wrapped-around number was small enough to sail
through.  The fix is to ask "is this already too big to take another digit?"
before multiplying.  One line.  The edge cases, the biggest and smallest
numbers that fit and one past each, now come out right both ways.

That's the first time on this ladder a test caught something we got wrong.
And it's the best argument I've got for the rule that every test has to be
able to fail.  A test that checks the program against its own idea of the
right answer would have passed with flying colours.

## What can end the machine

Divide by zero.  On your laptop, the processor raises its hand, the operating
system catches it, and your program dies with a message.  This machine has
nobody to catch it, because nothing has asked for that yet.  So the fault
turns into a bigger fault turns into a reset, and the virtual machine takes a
reset to mean "we're done."  The calculator would just vanish mid-sentence.
So it checks before dividing.  It also refuses the one sneaky division that
overflows: the most negative 32-bit number divided by minus one, which has no
32-bit answer at all.

Catching crashes is a real job for an operating system, and a good one.  It's
where the landlord learns to evict a tenant who breaks things.  It'll be its
own rung when something needs it.

## The ladder held

Hello world, Hanoi and Life all run on loader version 3 with no change to any
of them.  Four programs, three loaders, and every old program still boots on
every new one.

Hit F5, pick calc, and type at it.  Try to break it.  I'd love to know if you
can.

## Read along

If you want to see it for yourself, these are the files to read, in this order.

1. [pool/CMP.calc@1/calc.c](https://github.com/cmcluckie/aios/blob/main/pool/CMP.calc@1/calc.c).  Start with the function called number.  The comment in it is the bug the test caught, and the one-line fix.  Then _start at the bottom: the whole keyboard handling, echo and backspace included.
2. [tests/fixtures/calc_ref.py](https://github.com/cmcluckie/aios/blob/main/tests/fixtures/calc_ref.py).  The same calculator, written again in Python from the same rules.  This is what the real one gets compared against, byte for byte.
3. [tests/fixtures/calc.in](https://github.com/cmcluckie/aios/blob/main/tests/fixtures/calc.in).  The keystrokes the test types.  99999999999 is in there.
4. [lifted/CMP.serial.8250@2/serial8250.c](https://github.com/cmcluckie/aios/blob/main/lifted/CMP.serial.8250@2/serial8250.c).  Scroll to the bottom: serial8250_poll and serial8250_getc.  That's the whole receive side, taken from Linux.
5. [pool/CMP.loader@3/loader.c](https://github.com/cmcluckie/aios/blob/main/pool/CMP.loader@3/loader.c).  door_read.  Wait for one byte, then take whatever else is already there.

## Addendum: the tests

Every test written for the parts above: what it checks, what turns it red, and whether it has actually been run.  "Checked by hand" means it was run and compared, but not yet by the automatic test runner (plan section 4), which doesn't exist yet.  Until it does, these are honest notes, not a scoreboard.

**calc@1**

- [calc.transcript@1](https://github.com/cmcluckie/aios/blob/main/tests/calc.transcript@1.toml).  Checks: Given a sequence of typed bytes, the component writes exactly what an independent reference implementation of the same reverse-Polish rules writes for that sequence, including echo, errors and the final bye, and exits only on q, quit, Ctrl-C or Ctrl-D.  Goes red when: with tests/fixtures/calc.in fed to the serial port, the bytes written differ from what tests/fixtures/calc_ref.py writes for the same input, or the machine is still running at the timeout.  Status: Checked by hand, 2026-10-11.  First run went red at byte 320 and caught a real bug (99999999999 wrapped around).  Green, 424 bytes exact, after the fix.

**loader@3**

- [loader.read@1](https://github.com/cmcluckie/aios/blob/main/tests/loader.read@1.toml).  Checks: The read door waits for at least one byte, then returns the bytes already received, in order, up to the requested count, and never more; write, exit and alloc keep their offsets and their behaviour from CMP.loader@2.  Goes red when: with tests/fixtures/calc.in fed to the serial port, CMP.calc@1 under this loader does not produce the reference transcript, or hello, hanoi or life under this loader differ by one byte from their outputs under the loader they were built for.  Status: Checked by hand, 2026-10-11: the calculator transcript is exact under this loader, and hello, Hanoi and Life are byte-identical under it.

**serial.8250@2**

- [serial.receive-order@1](https://github.com/cmcluckie/aios/blob/main/tests/serial.receive-order@1.toml).  Checks: Every byte that arrives on the serial port is handed to the read door once, in order, with none lost and none invented.  Goes red when: a program that echoes every byte it reads, fed 4096 bytes of every value but 3 and 4 in a fixed order, writes back anything other than those 4096 bytes in that order.  Status: Not run yet.  It needs an echo program.
