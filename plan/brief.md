# AiOS project plan (brief)

One sentence per item.  Status in brackets: [done], [in progress], [coming up], [parked].
[parked] means decided not now, with the reason in the item.
The detailed plan is plan/full.md; this file is the one to read.

1. Constitution: the signed repo everything traces to. [done]
   1.1. Repo rules, ten tenets and purpose 0000 committed. [done]
   1.2. Petition schema with the catalogue tables and referee rules. [done]
   1.3. Petition 0000, hello world, written against the schema. [done]
   1.4. Findings 0000, the thirteen schema gaps, recorded. [done]
   1.5. Define the entry file formats for CAP, component, SPEC, TST and SNS. [done]
   1.6. Fix the review signing scheme so signatures live outside the file they sign. [done]
   1.7. Resolve the remaining gaps and publish the schema at version 2. [done]

2. The jig: the gen-zero host that turns the crank. [in progress]
   2.1. NixOS minimal on the existing box with one configuration of about twenty lines. [done]
   2.2. Bare git repo on the Pi over SSH that rejects unsigned commits. [in progress]
   2.3. Every installed tool has a complete row in the tool table, including how it leaves. [done]
   2.4. KVM and QEMU VM definition with one serial port and no NIC, as a petition. [done]

3. Referee: no model, no judgment, fails loud. [in progress]
   3.1. Resolver that checks every catalogue number resolves to an entry at a version. [in progress]
   3.2. Relation checker for rules 1 to 10 that reports a rule number and a catalogue number, nothing else. [coming up]
   3.3. Expiry, status and quorum enforcement. [coming up]
   3.4. Artifact check for rule 11: the built image and VM against the petition. [coming up]
   3.5. Commit and review signature verification against constitution/keys. [coming up]
   3.6. Decision ledger: every agent decision declared with its options and who chose, checked against the diff so an undeclared one fails, with a human-only list; built before the committee. [coming up]
   3.7. The referee runs the tester itself after every build, against that exact image, and says yes or no; the cache (5.4) takes only an image with that yes. [coming up]

4. Tester: manufacture failures before the world does. [in progress]
   4.1. Runner that boots the machine and captures every byte on the serial port; the shadow VM comes with 5.3. [done]
   4.2. Executable form of TST.hello.exact-bytes, and every other test, bound to the runner. [done]
   4.3. Mutation script that breaks the code on purpose and proves each test goes red. [done]
   4.4. Sensor runner for SNS.hello.boot-to-output with the threshold as a number. [coming up]

5. Builder: turn an approved petition into the system, deterministically. [in progress]
   5.1. Translator from a flavor to a build; a shell script now, a Nix expression when the jig exists. [in progress]
   5.2. Build that reproduces bit-identical on two hosts. [coming up]
   5.3. Live and shadow copies, swapped by the referee only on a passing shadow. [coming up]
   5.4. A launch names its applications; the first launch of a combination builds the nucleus for it, later launches reuse that build, keyed by exactly which applications at which versions. [coming up]
   5.6. The builder works from a queue anyone can read: it builds what it can, sends the full list of what is missing to the quartermaster, and stops; an admission puts the flavor back in the queue and the run starts again from the referee. [coming up]
   5.7. Each part's compiled objects cached by exactly what went into them, so a rerun compiles only what changed; make and ccache are the history. [coming up]
   5.5. Adding an application without rebuilding the nucleus: today a new application means a new petition, new parts and a rebuild of the whole nucleus, worse than adding a driver to early Linux; Linux's answer then was loadable modules, the history to start from. [parked]

6. Pool admission of what petition 0000 needs: parts, not a kernel. [in progress]
   6.1. PART.hello@1: C against the loader's two system calls, no libc, with its as-built spec and catalogue entry. [done]
   6.2. TOOL.c@1: a C compiler admitted as the smallest reviewable unit. [coming up]
   6.3. PART.serial.8250@1: the byte-on-the-wire lines lifted from Linux, hands cut, spec and test written here. [done]
   6.4. PART.loader@1: takes over from the machine, sets up the processor, runs one program, halts when it exits; boot path lifted from Linux where it helps. [done]
   6.5. The system calls: how hello asks the loader to write and to exit, fixed as SPEC clauses so petition 0001 stacks without a swap. [done]
   6.6. Signed admission of each by the root key until committee seats exist. [coming up]
   6.7. First green build of 0000 with its bloat figure recorded; every unjustified line is a finding. [done]

7. Quartermaster: decide what enters the ecosystem. [coming up]
   7.0. One shared source reader for the quartermaster and the historian, built first: a mechanical half (cscope by default, no model) and an AI half on top; not an agent; findings 0015. [coming up]
   7.1. Catalogue derived from source: components, dependencies, exposed capabilities. [coming up]
   7.2. Build failures mapped to catalogue numbers, never raw tool output. [coming up]
   7.3. Pool-admission petitions drafted automatically from a failure. [coming up]
   7.4. Linux parts classified as liftable, tangled, or not needed, starting from what the ladder will ask for. [coming up]
   7.5. Capabilities as labels: every component carries the capabilities it may use as its label, the quartermaster drafts them from the source, the decision ledger records each, a new capability is human-only, the nucleus enforces them; findings 0013. [coming up]
   7.6. Open question, not decided: when a mechanic's fix touches lifted lines, does the quartermaster decide whether it goes back upstream to Linux?  Every Linux patch carries a person's Signed-off-by, so the answer has to cover who signs. [parked]

8. Committee: competing priorities, slow policy. [coming up]
   8.1. Six seats on separate models, each bias written down: security, performance, portability, experience, stability, purpose-fit; with six, the quorum rule says how a tie is broken. [coming up]
   8.2. Quorum rules fixed in advance and tested under deadlock. [coming up]
   8.3. Seat keys in constitution/keys and review signing that works. [coming up]
   8.4. Petition 0000 approved by a real review. [coming up]

9. The ladder: one textbook program per petition, each fails on exactly one new thing. [in progress]
   9.1. Petition 0001, Towers of Hanoi: recursion, output only; no new system call, no new line in the loader, proving a second program changes nothing. [done]
   9.2. Petition 0002, Conway's Game of Life: the program asks for memory; the loader reads the machine's memory map and hands out pieces of it. [done]
   9.3. Petition 0003, a reverse-Polish calculator: the program reads; the serial part gains a receive side and the loader a read system call. [done]
   9.4. Petition 0004, a stopwatch: ticks once a second, counting up on one line until switched off; the program needs time passing, the microvm clock debt becomes a petitioned capability and the first real sensor. [done]
   9.5. Petition 0005, save the sorted output: an IDE disk driver and the original Minix filesystem lifted from Linux, the first expensive lift. [done]
   9.6. Petition 0006, two programs at once: the first thing that must be shared; the kernel appears, and every line of it is named. [done]
   9.7. Petition 0007, the console text editor: open, type, save; needs 0003 and 0005; C now, Rust later as PART.editor@2. [coming up]
   9.8. Every earlier program runs under every later loader; no system call ever moves. [in progress]
   9.9. The loop end to end: the quartermaster drafts the application's petition, the builder sends what is missing, the quartermaster drafts the parts, the committee votes, the flavor goes back in the builder's queue; the mechanic proposes and never installs. [coming up]
   9.10. The first Linux binary: a static Linux hello world runs unmodified on two system calls; every further Linux system call is petitioned by the first program that needs it. [coming up]
   9.11. BusyBox vi, unmodified: the capstone Linux binary, its system calls found by tracing it, each one a petitioned capability. [coming up]
   9.12. The clock on the screen: the time of day, not just time passing; the petition argues for a clock chip or asking the host. [coming up]
   9.13. Programs lose the kernel's privilege: they run in ring 3 and the system call table becomes a gate they cannot step around; parked to get back to the components around the nucleus. [parked]

10. Lifecycle: grow, prove, strip, seal, molt. [coming up]
   10.1. Gateway as the only component that talks to the outside. [coming up]
   10.2. Strip everything without a live petition and prove the seed regrows it. [coming up]
   10.3. Watchman and the molting rule decided while the system is still smart. [coming up]
   10.4. First sealed run of hello with no model and no outbound connection. [coming up]

11. Historian, cartographer and bare metal. [coming up]
   11.1. Historian records what worked, pushes to the Pi, watches upstream against every origin record and lifts again through the door. [in progress]
   11.2. Cartographer maps hardware on arrival from datasheets, never trial and error. [coming up]
   11.3. Purpose agent weights the committee's priorities per machine. [coming up]
   11.4. Gen two: a machine whose purpose is to build other instances of itself. [coming up]
   11.5. Gen two rebuilds itself bit-identical to what gen zero made; the jig retires. [coming up]
   11.6. First bare-metal machine built by petition. [coming up]
   11.7. Which Linux branches AiOs follows (mainline, stable, long-term support) is a setting; the historian weighs a fix by the branch it is on. [coming up]
