# Findings 0050: car 3 laid out, petition 0016

Source: part 24, 2026-11-25, out/car3.sh on the jig at the commit with findings
0049, and the builder and referee run in Claude's workspace.
Goes to: the architects (Chris and Claude).

1. **With the sharing parts, car 3 runs, all but Dave's.**  On the jig for 15
   seconds: the stopwatch showed 00:00 to 00:14, BYTE's sieve printed "1899
   primes, 800 times over, in 7 ms", and program 3, Dave's sieve, stopped at
   once: "Guru Meditation #0000000E.00000000".  TST.gate.drag-shares@1: "the
   sieve printed no result line".

2. **Why.**  The sharing kernel (PART.share@2) copies each program in its
   archive byte for byte to the bottom of its own 8 MiB and asks the gate for a
   space that starts there (gate_space_new).  Only the lone kernel's loader
   (PART.loader@10, elf_run) reads a Linux program file; the sharing kernel
   never does, so the gate starts Dave's file at its first byte, the ELF
   header.  The Linux calls' memory (brk_lo, map_lo, the holes) is also one set
   for the whole gate, not one a space.

3. **One part can do it.**  A fix is the files of one part (decision 0060).  The
   gate is handed every program's bytes and space; it can tell a Linux program
   file from the first bytes, put its pieces where the file says inside the
   space, lay out its starting stack and start it with the Linux calls, as
   gate_exec does for a lone one.  PART.share@2 is not touched.

4. **Petition 0016.**  PART.gate@3 and PART.loader@11, copies of PART.gate@2
   and PART.loader@10 but for their headers, PART.loader@11 built on
   PART.gate@3.  SPEC.gate.16@1 and TST.gate.drag-shares@1 move to PART.gate@3.
   The dragshare flavor adds it.  Built in the workspace: PART.loader@11 with
   PART.gate@3, PART.share@2, the 8259, the 8254 tick and the cpio reader; the
   referee's rules give the same failures as before it, and every flavor still
   builds, but "both", refused by rule 19 as before.

   PART.gate@3, for the 3090.  The red: "the sieve printed no result line".
