1. **What part 21 is.**  The mechanic, the third agent in design.md's table
   (fix and refactor; may propose a patch; may not install anything, skip the
   quartermaster, or share a model or prompt with the quartermaster or the
   tester), does its first job.  Until now the mechanic was Claude.

2. **Ruled by Chris, 2026-10-21.**  (a) A straight comparison, A against B: Claude,
   the best model on Amazon Bedrock (number one), and the RTX 3090 running
   qwen3.8:27b on Ollama (number two), each make the same fixes.  It is a
   comparison only: which model gets which job, and when work goes from one to
   the other, is a later part, built on these numbers.  (b) Claude writes the
   3090's prompts.  A failure means the prompt was not good enough, and the next
   try is a better prompt, written by Claude from what went wrong.  The lesson,
   in Chris's words: if you don't know how to talk to an AI, ask the AI.  (c) The
   mechanic may or may not share a model with the quartermaster and the tester;
   it does not matter, and the best model available is the one to use.
   design.md's table said "may not share", which is not what was meant (decision
   0057).  (d) Fix everything left broken on purpose, not one thing: TECH-DEBT 1
   to 4 in findings 0021, and SSE (findings 0023 item 13).  Fixing is not the
   story; the pattern of why each one broke is, and the article can run longer
   for it.  (e) A fix is real only when every test passes, the whole suite on the
   jig, not only the test that was red.  (f) Everything is measured in tokens.
   The score is tokens per line of working code: the lines of the finished fix
   that passes everything, for the prompt version that worked.  How many prompt
   versions it took, how long the final prompt is, the time, the card's power,
   and the tokens Claude spent writing the 3090's prompts are recorded for
   information and are not part of the score.  (g) Why it is measured this way:
   the 3090 may be the cheaper way to working code without looking it, and only
   a scorecard of what went in and what came out can say.  Chris's prediction,
   written down before the run: Claude knocks it out of the park and the 3090
   sucks; the numbers will say how badly.

3. **The five fixes, in plain words.**  TECH-DEBT 1: alloc, ms, load and save use
   the AiOs-only numbers 1000 to 1003.  Programs reach the kernel through the
   table of stubs the kernel hands them (findings 0021 item 3), so the fix stays
   in the kernel and no program is rebuilt.  TECH-DEBT 2: a program waiting in
   read stops every other program, the stopwatch with it.  TECH-DEBT 3: a
   program's window is rounded up to whole 4 MiB pages, so it can reach memory it
   was never given.  TECH-DEBT 4: AT_RANDOM's 16 bytes are the cycle counter; the
   processor has an instruction for random numbers (RDRAND) where it has one.
   SSE: AiOs never says it saves those registers, so a program built for a newer
   processor than the 486 stops on its first SSE instruction.

4. **Tests first.**  For most of the five, no test can see the problem yet
   (findings 0021 says so for TECH-DEBT 2), so a model could change nothing and
   still pass everything.  Before either model touches anything, Claude drafts a
   test for each that goes red on AiOs as it is; tests are human-only, and Chris
   decides them.

5. **What a model gets.**  The red test's file and what it printed, the test's
   red_when, and the reader on the repo as it stands.  Not the fix.  It hands in
   its fix through a tool (submit_fix: a path under pool/ and the whole new file),
   the way the draft step's model hands in a petition (decision 0043).

6. **The judge.**  The fix stands in its own copy of the repo; then the whole

   fix.  On the jig the suite takes about five minutes, so every try takes at
   least that long.  A green fix is a proposal; Chris decides whether it goes in.
