# Findings 0024: the mechanic

Source: part 21, 2026-10-21, Chris's notes and rulings of the same evening.
Goes to: the architects (Chris and Claude).
Part 21 goes out 2026-11-15.

1. **What part 21 is.**  The mechanic, the third agent in design.md's table
   (fix and refactor; may propose a patch; may not install anything, skip the
   quartermaster, or share a model or prompt with the quartermaster or the
   tester), does its first job.  Until now the mechanic was Claude.

2. **Ruled by Chris, 2026-10-21.**  (a) A straight comparison, A against B: Claude,
   the best model on Amazon Bedrock (number one), and the RTX 3090 running
   qwen3.8:27b on Ollama (number two), each make the same fixes.  It is a
   comparison only: which model gets which job, and when work goes from one to
   the other, is a later part, built on these numbers.  (b) Claude writes the
   3090's prompts.  A failure means the prompt was not good enough, and the next
   try is a better prompt, written by Claude from what went wrong.  The lesson,
   in Chris's words: if you don't know how to talk to an AI, ask the AI.  (c) The
   mechanic may or may not share a model with the quartermaster and the tester;
   it does not matter, and the best model available is the one to use.
   design.md's table said "may not share", which is not what was meant (decision
   0057).  (d) Fix everything left broken on purpose, not one thing: TECH-DEBT 1
   to 4 in findings 0021, and SSE (findings 0023 item 13).  Fixing is not the
   story; the pattern of why each one broke is, and the article can run longer
   for it.  (e) A fix is real only when every test passes, the whole suite on the
   jig, not only the test that was red.  (f) Everything is measured in tokens.
   The score is tokens per line of working code: the lines of the finished fix
   that passes everything, for the prompt version that worked.  How many prompt
   versions it took, how long the final prompt is, the time, the card's power,
   and the tokens Claude spent writing the 3090's prompts are recorded for
   information and are not part of the score.  (g) Why it is measured this way:
   the 3090 may be the cheaper way to working code without looking it, and only
   a scorecard of what went in and what came out can say.  Chris's prediction,
   written down before the run: Claude knocks it out of the park and the 3090
   sucks; the numbers will say how badly.

3. **The five fixes, in plain words.**  TECH-DEBT 1: alloc, ms, load and save use
   the AiOs-only numbers 1000 to 1003.  Programs reach the kernel through the
   table of stubs the kernel hands them (findings 0021 item 3), so the fix stays
   in the kernel and no program is rebuilt.  TECH-DEBT 2: a program waiting in
   read stops every other program, the stopwatch with it.  TECH-DEBT 3: a
   program's window is rounded up to whole 4 MiB pages, so it can reach memory it
   was never given.  TECH-DEBT 4: AT_RANDOM's 16 bytes are the cycle counter; the
   processor has an instruction for random numbers (RDRAND) where it has one.
   SSE: AiOs never says it saves those registers, so a program built for a newer
   processor than the 486 stops on its first SSE instruction.

4. **Tests first.**  For most of the five, no test can see the problem yet
   (findings 0021 says so for TECH-DEBT 2), so a model could change nothing and
   still pass everything.  Before either model touches anything, Claude drafts a
   test for each that goes red on AiOs as it is; tests are human-only, and Chris
   decides them.

5. **What a model gets.**  The red test's file and what it printed, the test's
   red_when, and the reader on the repo as it stands.  Not the fix.  It hands in
   its fix through a tool (submit_fix: a path under pool/ and the whole new file),
   the way the draft step's model hands in a petition (decision 0043).

6. **The judge.**  The fix stands in its own copy of the repo; then the whole
   suite, the referee's rules and the ledger.  Green everywhere or it is not a
   fix.  On the jig the suite takes about five minutes, so every try takes at
   least that long.  A green fix is a proposal; Chris decides whether it goes in.

7. **Recorded for information.**  The card's power is logged on the Windows side
   (nvidia-smi, once a second, during a run) and copied in, since the jig cannot
   see the card; Claude's runs have no power figure.

11. **The five tests, red (2026-10-22, in Claude's workspace, under software
    emulation, not the jig).**  Each drafted for Chris to decide; each red on
    AiOs as it is, for the reason it names.
    (a) TST.gate.linux-only@1 (SPEC.gate.10): a Linux program calling 1000 to
    1003 under the cat flavor's kernel is answered 0, 0, -14, -14, not Linux's
    -38.  (b) TST.loader.random@1 (SPEC.loader.15): three boots, and two
    AT_RANDOMs agree in 8 of their 16 bytes; the last eight are the counter's
    high half, the same on every boot.  (c) TST.gate.sse@1 (SPEC.gate.11): a
    program built with -msse2 stops with Guru Meditation #00000006, as cat's
    probe did on the jig in part 20.  (d) TST.gate.window-end@1 (SPEC.gate.12):
    on the cat flavor's machine given 62 MiB instead of 64, so the window does
    not end on a 4 MiB line, a plain program reads the first byte past its
    window and carries on.  (e) TST.share.waits@1 (SPEC.loader.16): on the gate's
    sharing kernel, a program waiting for a byte that never comes freezes the
    stopwatch beside it before 00:00.  On the sharing kernel from before the gate
    the same probe is green: there a call is a plain function call with
    interrupts on, so TECH-DEBT 2 is the gate's alone.
    Where each debt is fixed follows from where its test sees it: (a) to (d) in
    PART.gate@2 and PART.loader@10, (e) in PART.loader@9 (the gate's sharing
    kernel).  The older copies (PART.gate@1's numbers and window, PART.loader@10's
    door_read) keep their marks and their entries until a test sees them.
    Not part of the tests: building the gateshare flavor prints "sed: can't read
    : No such file or directory" from jig/aios; the build succeeds.  Noted, not
    yet traced.

14. **Try 1: Sonnet and a bug in the bench (2026-10-22, on the jig at 2a35b7e).**
    jig/fix gate.linux-only@1 with Sonnet 4.6 and fix/prompt.txt (ad43d5b5): no
    fix handed in, 40 calls used, recorded as refused; 41 input tokens, 1,686,060
    read from the cache, 77,458 written to it, 8,830 out, $0.928859.  The bench's
    fault, not the model's: the look tool took a range only as FIRST-LAST, Sonnet
    asked for lines as two numbers ("340 480"), and the tool quietly sent the file
    from line 1 every time.  Sonnet said so ("the read command always reads from
    the beginning") and spent about 15 calls working round it with find.  It still
    found the four AiOs-only numbers, that old programs reach them through the
    stubs in gate_user.S, that brk_lo tells a Linux program from an old one, and
    that TST.gate.debt-listed holds every TECH-DEBT mark to findings 0021.  Also:
    find ignored the folder it was given, and the summary line left out the
    tokens read from the cache, which were nearly all of them.  All three fixed
    (decision 0061); try 2 uses the same prompt, since the prompt was not what
    failed.

15. **Try 2: the same bench bug, a second way (2026-10-22, on the jig at f216fd5).**
    Sonnet 4.6, the same prompt (ad43d5b5): refused again, 40 calls, 41 input
    tokens, 2,152,466 read from the cache, 89,048 written to it, 11,031 out.
    Sonnet asked for line ranges with fields it named itself, start_line and
    end_line, which were not in the tool's description, and the tool ignored
    them; seven reads came back from line 1.  It said so again and found its way
    with find.  It worked out more than on try 1: which ladder programs use
    alloc, ms, load and save (hello and hanoi do not), that gate_user.S is the same
    in gate@1 and gate@2, and how loader@10 hands old programs their table.  The
    tool now takes start_line and end_line and names them in its description, and
    every read is headed with the file, the lines shown and how many it has, so a
    model can see when it did not get what it asked for (decision 0062).  The
    lesson for the series: a tool for a model has to accept the way a model asks,
    and say plainly what it did.

16. **Try 3: a pass, and not the fix (2026-10-22, on the jig at 9183f99).**  Sonnet
    4.6, the same prompt (ad43d5b5), the look tool working: the judge said pass,
    the red test green and nothing green gone red, 25 lines changed, 29 calls; 30
    input tokens, 1,061,291 read from the cache, 75,652 written to it, 19,144 out.
    The first fix a model wrote for AiOs that every test passed.  Not taken: in
    PART.gate@2 a Linux program now gets -38 at 1000 to 1003, and old programs

    behavior"); its comment in the file, "TECH-DEBT 1 (fixed here ...)", claimed
    more than it did.  The test's own last line had claimed too much as well: "no
    AiOs-only numbers left".  It now also holds the source to the spec: no NR_ of
    1000 or more in PART.gate@2/gate.c, no stub in its gate_user.S loading one.
    Shown in Claude's workspace: the old test passes try 3's change, the new one
    fails it on the four lines still there.  The run stays recorded as a pass,

18. **Try 5 broke cat, and the referee had never looked (2026-10-23, on the jig at
    b533217).**  Sonnet 4.6, prompt ffab2514, 37 calls: the judge said fail, 137
    lines changed.  TECH-DEBT 1's own test went green; five cat tests that were
    green went red, each with "save failed".  To take away the AiOs-only
    numbers, Sonnet sent the old table's save through open, write and close,
    and gate@2 refuses a program's open for writing (part 20, decision 0046).
    The cat tests' helper, tests/programs/catfiles.c, saves the files cat
    prints on cat's own kernel, through that save.  On its own terms the change
    was sound; what broke was a helper that should never have been able to
    write there.  Petition 0014
    asks for CAP.fs.read and not CAP.fs.write, and the quartermaster's petition
    (0013) asked the same: the petitions were right.  The kernel was not:
    PART.fs.minix@2 exposes both, and the builder takes a part whole.  Rule 11
    of schema/petition.md has said since the start that a built image exposes
    no capability not granted, checked against the artifact; the referee only
    ever checked the other way round, that what is asked for is there (rule 5).
    Run by hand on every flavor, the missing check found cat's write and more:
    eight older flavors' kernels expose mem.alloc, proc.exit or tty.read that
    their petitions never ask for.  Decision 0065: the builder hands each kernel
    the capabilities its flavor asked for as switches (GRANT_), PART.fs.minix@2
    compiles its writing in only when asked, the referee holds every linked
    kernel to rule 11 with nm, and the eight older flavors' extras are listed
    in constitution/extras.toml, a list that only shrinks (debt, not a pass).
    Rule 22: a test program boots only where every call it makes is asked for,
    listed or expected refused; catfiles.c now writes the disk on the editor's
    kernel, which asks to write.  Cat's kernel is now 24,852 bytes, from 29,048,
    and has no minix_save; every other kernel is byte for byte as it was.  The
    lesson for the series: a rule written down that no machine enforces is a
    note, and the first real change by a model found it.  Try 5's run record is
    in runs/ on the jig, with try 4's, until they are gathered into the repo.
