# Findings 0002: what the handoff forces, and what no petition justifies

Source: plan section 6, reading Linux (commit a5ebb76233b7), QEMU (615ece3c406b)
and qboot (the microvm firmware) to carve the segments petition 0000 names, then
building and booting them.  Goes to: humans who own the constitution.

## Result

Petition 0000 boots.  Fourteen bytes on the serial port, nothing before, nothing
after, and the machine exits by itself.  SPEC.hello.1 and SPEC.hello.2 are green
on the first boot, under software emulation in a container; KVM on the jig is
still to be seen.  170 lines of source across three segments: 57 lifted from
Linux for the serial port, 106 for the loader (41 assembly, 57 C, 8 header), 7
for hello.  Hello's own machine code is 27 bytes and contains no hardware
instruction at all.  The bloat figure, lines in the image no petition justifies,
is the list below, not a percentage.

## The handoff, as found

The microvm firmware is qboot (QEMU `pc-bios/qboot.rom`), selected only because
the machine says `acpi=off`; with ACPI on, microvm uses a SeaBIOS build, which
writes to the serial port.  qboot never writes to the serial port and its panic is
`cli; hlt`.  It reads the kernel, module and command line from the fw_cfg device,
builds an `hvm_start_info` block, and jumps to the ELF's `XEN_ELFNOTE_PHYS32_ENTRY`
address with `ebx` pointing at that block: 32-bit protected mode, flat code and
data segments with unspecified selectors, paging off, `cr4` clear, interrupts
off, no stack, no IDT (Linux arch/x86/platform/pvh/head.S lines 29-47 state the
contract; qboot fw_cfg.c `boot_pvh_from_fw_cfg` is the other side).

## Lines no petition names

1. **A GDT and a segment reload.**  The ABI leaves selectors unspecified, so the
   loader installs three descriptors (null, code, data) and reloads `ds`, `es`,
   `ss`, `cs`.  Eleven lines of assembly, lifted from head.S.  Unavoidable under
   this ABI.

2. **A stack.**  4 KiB of zeros and one `mov`.  The ABI gives none.  Unavoidable.

3. **An ELF container with a Xen note.**  QEMU's loader will only take a PVH entry
   from an ELF PT_NOTE segment.  The note is seven lines of assembly; the ELF
   format and link script exist for the hypervisor, not for us.  Unavoidable
   while the hypervisor is QEMU.

4. **Start-info parsing.**  Two struct definitions and a magic check, lifted from
   include/xen/interface/hvm/start_info.h, to find where the firmware put the
   program.  Unavoidable under this ABI.

5. **Copying the program to a fixed address.**  The firmware places the module
   wherever it likes.  Six lines.  Avoidable if the program were position
   independent; chosen so that hello links at one address and the as-built spec
   can say where it ran.

6. **A triple fault to halt.**  The machine has no power-off device and no
   petition asks for one.  The loader loads a null IDT and executes `int3`; the
   hypervisor sees a reset; `-no-reboot` makes the reset an exit.  Four lines.
   Honest alternative is a debug-exit device, which is a device and would need a
   CAP; the triple fault needs nothing.  This closes findings 0000 #15 for good:
   "halt" is a reset request the machine turns into an exit, and nothing prints.

7. **Serial port initialisation the hypervisor does not need.**  Nine register
   writes (8n1, interrupts off, FIFO off, DTR and RTS, divisor) kept because a
   real 16550 needs them.  QEMU's 16550 transmits regardless, so no test on the
   jig can turn these lines red; tenet 8 says they are decoration until a
   machine exists on which they are not.  Kept, and recorded.

8. **Devices the machine type forces.**  With PIC, PIT, RTC, ACPI and option ROMs
   off, microvm still presents: eight empty virtio-mmio transports, the IOAPIC,
   the ISA bridge, the fw_cfg port (which the firmware needs to find the kernel
   at all), and under KVM the kvmclock paravirtual device.  None can be switched
   off.  No component touches any of them.  SPEC.machine.1 is reworded to say
   so instead of claiming exactly one peripheral; TST.machine.no-peripherals
   names the allowed set.

9. **The firmware itself.**  qboot runs a few thousand lines before our first
   instruction: a real-mode IDT, PCI probing (finds nothing), MP table, SMBIOS,
   e820.  It is part of CMP.hypervisor.qemu (scaffold).  The first line that is
   ours is `cld` in start.S.

10. **The compiler's choices.**  Flags force 32-bit, freestanding, no PIC, no
    stack protector, no SSE, no unwind tables, no build-id.  What gcc still adds
    beyond the source is in the as-built specs; for hello it is one `sub $0x10,
    %esp` of frame alignment.  The toolchain is scaffold (CMP.toolchain.c@1).

## Decisions taken, recorded for the referee

- **32-bit protected mode, paging off.**  One program, one address space,
  nothing to translate.  Long mode would add PAE, EFER, page tables and a far
  return (head.S lines 90-160), all for a program that uses 43 bytes.  64-bit
  arrives when a petition needs more than 4 GiB or 64-bit arithmetic, as
  CMP.loader@2.

- **The door is a table of function pointers, 32-bit cdecl.**  A software
  interrupt or `syscall` would need an IDT and a privilege boundary; with one
  tenant there is nobody to be protected from, and the hardware boundary would be
  theatre.  The door is a convention, and the as-built spec is what enforces
  it: hello's lists no hardware instruction.  When a second tenant arrives, the
  door moves behind a privilege boundary and the table layout stays.

- **A kernel of kind `kernel`.**  CMP.loader@1 is entered in the index as kind
  `kernel` because that is the role it plays: the landlord.  It is 572 bytes.
