# Findings 0008: the stopwatch, and a clock you have to measure

Source: petition 0004, a stopwatch, 2026-10-11.  First time passing.
Goes to: humans who own the constitution.

1. **The processor won't say how fast its counter ticks, here.**  Under
   software emulation, CPUID leaves 0x15 and 0x16 (the counter's rate) are
   empty, the "invariant counter" flag is clear, and the emulator's own leaf
   (it signs itself "TCGTCGTCGTCG") leaves the rate blank.  The counter does
   tick.  Chris chose the 8254 method on 2026-10-11, knowing modern Linux tries
   the processor and the hypervisor first and uses the 8254 as its fallback.

2. **The 8254 is back, for one job.**  New machine, CMP.machine.serial-timer@1:
   serial-only@1 plus pit=on.  The PIC stays off, so the timer interrupts
   nothing.  The loader reads it for about 50 ms at boot through
   CMP.timer.tsc-pit@1 and never touches it again.

3. **microvm has no port 0x61.**  Linux sets counter 2's gate through the PC
   speaker port, 0x61.  microvm has no speaker; port 0x61 reads 0xff.  QEMU's
   counter 2 counts anyway with its gate as it is, so the lifted code drops the
   two lines that write 0x61.  On a real PC that cut would matter; recorded so
   the bare-metal rung (plan 11.6) finds it.

4. **Linux's fast calibration fails about one try in three under emulation.**
   It refuses to answer when the high byte of the 8254's count changes before
   it has been read six times, or when the error estimate will not get under
   500 ppm.  Under the emulator, a host scheduling hiccup or the first pass
   through freshly translated code is enough.  Linux would fall back to its
   slow method, which needs port 0x61.  The loader instead tries the fast one
   up to five times.  Failures are refusals, never wrong answers: every success
   seen gave 2.800 GHz, within 0.03% of each other.  Before the retries the
   stopwatch hung at 00:00 on about half the boots; after, none in twelve.

5. **The answer is right.**  Over ten seconds by the host's clock the ms door
   drifts by 0 to 4 ms across runs (TST.loader.ms@1, TST.timer.rate@1), under
   0.05%, under emulation.  SNS.stopwatch.drift@1's threshold is 100 ms.  The sensor runner
   (plan 4.4) does not exist yet; the number is in tests/results.txt.

6. **The 1985 bug, on purpose.**  Mutations put back each way old software got
   time wrong: the stopwatch timing itself by counting its own loops, the
   counter assumed to tick at 1 GHz, the 8254 assumed to tick at 1 MHz, the
   machine without its timer.  Every one is caught.

7. **The emulated counter starts at zero.**  Under the emulator the time stamp
   counter starts near 0 when the machine powers on, so a door that forgot to
   subtract the loader's starting value would only be wrong by the boot time,
   tens of milliseconds.  TST.loader.ms@1 therefore requires the first reading
   to be 5 ms or less; the mutation that drops the subtraction reads 13 to 48.

8. **The stopwatch never halts, so its tests watch it instead.**  jig/test's new
   `timed` kind boots a machine that never halts, watches it for exactly N
   seconds by the host's clock, and stamps every line with the host's
   milliseconds as it arrives.  Built on GNU coreutils' `stdbuf` and `date
   +%3N`, already on the jig.

9. **Every earlier program runs under loader@4.**  TST.loader.ladder-4@1 boots
   hello, Hanoi, Life and the calculator, each built for its own loader, under
   loader@4 on the stopwatch's machine: byte-identical.

10. **Lines from Linux: 172.**  69 in the serial driver, 103 in the timer part,
    of which 8 are glue (a typedef, `#define asm __asm__` because this build is
    C11, `#define get_cycles() rdtsc()`, a pragma for -Wsign-compare, and the
    two exported functions).  Counted the way the 57 was: the .c files in
    lifted/, no blank lines, no comments.
